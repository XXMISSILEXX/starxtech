## A. Routes reachable without authentication

| Route | Reason |
|---|---|
| `GET /login` | `auth.login` ∈ `public_endpoints` (`app/__init__.py:153`), so `require_login` returns early. **Also issues a presigned S3 GET URL for the brand logo to anonymous clients**: `inject_shell_context` (`app/__init__.py:78-82`) → `get_current_branding()` → `create_presigned_download` (`app/branding.py:14-16`), rendered at `base.html:25,66`, which `auth/login.html:1` extends. The only pre-issuance check is the object's own `deleted_at`/`upload_status` (`app/branding.py:11`) — no authorization. Leaks bucket name, object key and a 300 s valid signature; also costs 2 unauthenticated DB queries per hit with no GET rate limit. |
| `POST /login` | Same public exemption; rate limited to `5 per minute` per remote address (`app/auth/routes.py:19`). Writes an `AuditLog` row per failed attempt (`:35-36`) with the attacker-supplied `login` string. |

No other route in scope is reachable unauthenticated: `require_login` is an app-level `before_request` and cannot be opted out per blueprint (A1 §1, re-verified at `app/__init__.py:155-167`). `health`/`healthz`/`static` are the only other public endpoints and are out of scope.

## B. Write/delete/admin routes with no proven RBAC **and** no capability check

None in this scope. Every route with `Writes? = YES` has at least one of a `@permission_required(...)` decorator, an inline `current_user.can(...)` gate, or a per-project capability check — **except** the three self-service routes where the mutation target is structurally `current_user` and no authorization beyond authentication is meaningful:

| Route | Reason it is listed as an exception rather than a finding |
|---|---|
| `POST /change-password` (`app/auth/routes.py:63-75`) | Writes `current_user.password_hash`; guarded by re-verification of the current password (`:66`). No RBAC applies to changing your own password. |
| `POST /account/` (`app/account/routes.py:17-24`) | Writes a `StorageObject` + S3 object; target is `current_user` (`:19`). Any authenticated user may set their own avatar by design. Worth noting that this makes S3 write + Pillow decode reachable by *every* authenticated user with no rate limit. |
| `POST /account/avatar/delete` (`app/account/routes.py:30-33`) | Soft-deletes only `current_user`'s own avatar object (`:31`). |

## C. Routes taking an ID with no owns-resource check

| `GET /admin/projects/<project_id>/reporters` and `GET /admin/projects/<project_id>/memberships` (`app/admin/routes.py:259-281`) | `db.get_or_404(Project, project_id)` (`:262`) with no verification that the caller has any relationship to that project — the only gate is the global `projects.view` permission (`:260-261`) plus the reports module gate. ## Caveats on this pass

- Module-gate states are taken from `FOUNDATION-A1.md` §2 and re-verified against the route files and `app/__init__.py:169-189`. One correction to A1 §2: its count of "11 explicitly named `admin.*` endpoints" includes `"admin.projects_memberships"`, which does not resolve to any registered endpoint — the effective count is **10**, and the membership write routes are ungated (D2).
- Template output safety (Jinja autoescaping of `AuditLog.user_agent`/`ip_address` in the storage dashboard's `events`, and of user-controlled `full_name`/`username`/`original_filename` in admin tables) was **not** audited here — only the route layer. Did not read `app/templates/admin_storage/index.html` or `admin/users/index.html`.
- I did not read the tests for these blueprints, so no claim is made about which of the divergences above are covered by a regression test.
- Reachability statements about who holds which permission code are derived from `app/permissions/registry.py`'s `DEFAULTS` (`:98-112`). Per A1's NOT-GUARANTEED list, DB grants are only ever synced by an explicit `flask sync-permissions`, so a live deployment's actual grants may differ from `DEFAULTS`; the code-level `SUPER_ADMIN` bypass (`app/permissions/services.py:17-18`) is the only grant that is guaranteed independent of DB state.
