## Unit 6b required deliverable — cycle and depth handling in the `tree` view

**Question asked:** does the recursive company/department tree at `app/partner_relations/routes.py:145` use a recursive CTE with a depth limit, an application-level visited set, or nothing at all?

**Answer: none of the three at read time. There is no recursive CTE, no depth limit, and no visited set in the tree builder. Cycle prevention exists only at write time, in a different blueprint, as an application-level BFS.**

Evidence, in order of the data flow:

1. **The write-side guard is real but lives elsewhere.** The only HTTP-reachable writer of `CompanyDepartment.parent_department_id` in the whole app is `app/partner_companies/routes.py:341` (`_save_department`) — confirmed by grepping every assignment to that column repo-wide (the only other writer is `app/cli.py:1056`, a seeding command, not HTTP-reachable). It rejects self-parenting (`:326-327`) and descendant-parenting (`:328-329`) using `_department_descendant_ids` (`:352-370`), which is an **application-level BFS with a `descendants` visited set** and therefore terminates. It also forces `parent.company_id == company.id` (`:322-323`), so cycles cannot cross company boundaries.

2. **The read-side has no protection whatsoever.** `_build_department_tree` (`app/partner_relations/routes.py:323-355`) builds `by_parent` from `parent_department_id` (`:331-332`) and then recurses:
   ```python
   def build_department(department):
       ...
       "children": [build_department(child) for child in sorted(by_parent.get(department.id, []), ...)],
   ```
   (`:341-350`). No `depth` parameter, no `seen` set, no `LIMIT`. Given a cycle among active departments this recurses until `RecursionError` → generic 500 (FOUNDATION-A1 §6: no traceback leaks, but the request dies). The Jinja macro `render_department` (`app/templates/partner_relations/tree.html:3-46`) recurses a second time over the same structure, so even if the Python builder were fixed the template would need the same guard.

3. **Two further unbounded traversals in the same file are worse than the recursion, because they hang rather than raise.** `_visible_department_ids` (`:372-377`):
   ```python
   current = department.parent_department_id
   while current:
       matching_ids.add(current)
       parent = by_id.get(current)
       current = parent.parent_department_id if parent else None
   ```
   has **no visited set** — a two-node cycle loops forever, tying up a Gunicorn worker indefinitely (reachable only when `q` is non-empty, `:363-365`). `_department_subtree_ids` (`:381-392`) has a `result` set but appends to `pending` unconditionally (`:391`), so it also never terminates on a cycle.

4. **The database provides no backstop**, exactly as `FOUNDATION-A2.md` §1/§2 flagged: `models/partner.py:39-44` declares `parent_department_id` as a self-referential FK with `ondelete="SET NULL"` and no check constraint, and there is no trigger. So the *only* thing standing between a cycle and a hung/500ing tree view is `_save_department`'s two `if` branches in another blueprint.

5. **The `PartnerRelationship.parent_relationship_id` half of A2's finding is not reachable at all.** Grepping the entire `app/` tree for `parent_relationship_id` returns exactly two hits: the column declaration (`app/models/partner.py:209`) and the relationship (`:221`). **No route, service, or CLI ever reads or writes it.** It is a dead column; its missing cycle constraint cannot be exploited today. (`app/partner_relations/routes.py:254-274` `_save_relationship` never touches it.)

6. **The partner-level parent graph (`parent_partner_id`) *does* have an application-level visited-set cycle check, and it is defeatable.** `_creates_cycle` (`:490-507`) walks ancestors with `seen` and terminates correctly. But it builds its edge map with `parent_by_partner.setdefault(row.partner_id, row.parent_partner_id)` (`:498`) — **one parent edge per partner**, first row wins by the `_relationship_rows` ordering (`:315-320`). Since `manage_company` enforces no uniqueness on `(company_id, partner_id)` and `models/partner.py:186-215` has no such constraint, a partner can hold two relationship rows with different parents. Concretely: create `R1(partner=A, parent=B)` and `R1b(partner=A, parent=C)`; then create `R2(partner=C, parent=A)`. When validating `R2`, `_creates_cycle` sees only `A→B`, walks `C→A→B→∅` and returns `False`, while the real graph contains `A→C→A`. Reachable by any holder of `partner_relations.manage`.
   **Blast radius of that cycle is limited**, and I checked why rather than assuming: nothing traverses `parent_partner_id` recursively at render time. `_build_department_tree` groups relationship rows flatly by `department_id` (`:328-329`), and `tree.html` never follows `parent_partner`. So a partner-level cycle corrupts the displayed reporting hierarchy but does not hang or crash the tree view. **The department-level cycle is the one that would.**

**Net assessment:** the tree route terminates today only because the department writer happens to be correct. Severity of the reader gap is bounded by "no currently-reachable route can create a department cycle", which makes it a defence-in-depth finding rather than a live DoS — but it is one bad migration, one CLI seeding run (`app/cli.py:1056` does not cycle-check), or one future editor of `parent_department_id` away from a worker-hanging 500 with no depth limit to catch it.

## A. Routes reachable without authentication

**None.** All 88 rows require an authenticated session.

Verified rather than assumed: `require_login` (`app/__init__.py:155-167`) is registered on the **app**, not a blueprint, so no blueprint in this group can opt out; its public allow-list at `:153` is exactly `{"auth.login", "health", "healthz", "static"}`, and no endpoint name in this group appears in it. The `request.endpoint is None` bypass (`:159-160`) only applies to unmatched URLs, which by definition are not these routes.

Two adjacent notes, neither an unauthenticated path:
- The `partner_*` blueprints' own `@bp.before_request` hooks run **after** `require_login` (Flask evaluates app-level hooks first), so they never see an anonymous user; `can_access_partners_module` (`app/auth/permissions.py:68-70`) would return `False` for one anyway.
- Presigned download URLs issued by the four `photo*preview` routes are unauthenticated bearer URLs at the S3 layer for their 300 s TTL (`STORAGE_DOWNLOAD_URL_TTL_SECONDS`, FOUNDATION-B §2). Obtaining one requires an authenticated request, so this is not an unauthenticated *route*, but the resulting object is fetchable without a session and cannot be revoked.

## C. Routes taking an ID with no owns-resource check

Structural note first: **the entire partner suite has no per-object, per-tenant or per-project scoping by design.** `partners.view` / `partner_companies.view` / `partner_fields.view` / `partner_field_collections.view` / `partner_relations.view` each grant module-wide read of every partner, company, department, field and relationship. So for the 45 partner-suite rows, "no owns-resource check" is the intended model, not a defect; what matters there is only the child-under-wrong-parent class, which I checked individually.

Routes taking an ID where a real check is missing or thinner than its siblings:

1. `POST /projects/<pid>/contractors/<role_path>` — `contractor_id` (form). `project_operations/routes.py:265`. No `can_access_contractor`. Leads to read/manage escalation over any active `ProjectContractor` (mechanism spelled out in the table row).

**D-0 — Required confirmation: the `archive` / `deactivate` / `restore` triplets in `partners/routes.py` and `partner_companies/routes.py` have NOT diverged.** Read side by side:

Both files use the same `app/partners/lifecycle.py` helpers (`:21-26`), both `deactivate` routes are pure delegations to `archive` (so the decorator runs twice — harmless), and both `restore` routes require the dedicated `.restore` code. The genuine divergences:

1. **`customers.move_project` vs `edit`/`archive`/`restore`** — `customers/routes.py:179` checks `can_access_customer` only; `:128`, `:139`, `:157` all check `can_access_customer` **and** `can_manage_customer`. 2. **`project_update_delete` vs `project_update_edit`** — `project_operations/routes.py:443-445` has no author scoping; `:425` (`_can_edit_update`, `:337-340`) does. Delete is broader than edit.
3. **`project_contractors` POST vs `project_update_new`** — `:397` explicitly rejects `assignment.project_id != project.id`; `:265` performs no equivalent check on the submitted `contractor_id`. Two routes in the same file, one validates the child-to-parent link, the other does not.
4. **`project_contractors` POST vs the four contractor routes** — `contractor_detail:168`, `contractor_edit:204`, `contractor_archive:225`, `contractor_restore:241` all call `can_access_contractor`; `:265` does not, despite consuming the same object type.
5. **`partner_companies.edit` POST vs every other mutation in its file** — `:189` omits `_require_active_company_for_mutation`, which `departments_new:154`, `departments_edit:167` and `departments_delete:176` all apply (and which `partner_relations` applies at `:93`, `:116`, `:134`). 6. **`photo_preview` (GET) vs `photo_signed_preview` (POST), in both partner files** — `partners/routes.py:200-201` and `partner_companies/routes.py:111-112` catch `PartnerPhotoError` and return a 404 JSON; `partners/routes.py:210` and `partner_companies/routes.py:120` call `signed_preview(...)["url"]` bare, so a record with no photo (or a photo whose `StorageObject` is `deleted`/non-`active`, per `partner_photos.py:34`) raises an uncaught `ValueError` → **500**. Same divergence, duplicated identically in both files. The GET variants additionally place the presigned URL — a bearer credential per FOUNDATION-B §2 — in a `Location` header, browser history and proxy logs, which the POST/JSON variants avoid.
7. **`is_active` form default, three helpers vs one** — `_save_company` (`partner_companies/routes.py:242`), `_save_department` (`:344`) and `_save_collection` (`partner_field_collections/routes.py:81`) all use `request.form.get("is_active", "on") == "on"`, so the checkbox rendered at `app/templates/partner_companies/form.html:22`, `department_form.html:31` and `partner_field_collections/form.html:22` **cannot be unchecked** — the browser omits unchecked checkboxes, the default re-asserts `True`, and the user's action is silently discarded. `save_field_definition` (`app/partners/services.py:247`) uses `form.get("is_active") == "on"` with no default, which is the correct semantics, and its template (`partner_fields/form.html:18`) renders the same kind of checkbox. Three of the four sibling save helpers are wrong in the same direction.
8. **`_company_or_404` lifecycle filtering inside `partner_relations`** — `index` filters `Company.deleted_at.is_(None)` (`:38`), but `company:70`, `manage_company:87`, `edit_relationship:110`, `delete_relationship:133` and `tree:148` all use `_company_or_404` (`:510-511`) with no lifecycle filter. Not an escalation (same permission both ways), but an inconsistent lifecycle surface across siblings in the same module family.
