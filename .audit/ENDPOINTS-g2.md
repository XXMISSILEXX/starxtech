## B. Write/delete/admin routes with no proven RBAC or capability check

1. **`POST /reports/projects/<project_id>/reports/create`** (`projects.reports_create_legacy_post_rejected`, `app/projects/routes.py:130`) — the *only* route in scope with no capability check of any kind; `_project_or_404(project_id)` `:131` verifies existence only. Writes nothing (returns 405), so impact is limited to project-existence disclosure (404 vs 405) to any reports-module user.

2. **`POST /attachments/<attachment_id>/delete`** (`app/attachments/routes.py:85`) — permanently deletes an attachment and its S3 bytes with **only** `can_edit_report` `:88`. The `report_attachments.delete` RBAC grant that the UI requires (`app/reports/routes.py:178`) is never enforced server-side, and no route anywhere checks `report_attachments.view`/`report_attachments.download` either.

3. **`POST /reports/issues/<issue_id>/delete`** (`app/issues/routes.py:147`) — soft-deletes a business record; `can_delete_persistent_issue` resolves to `can_edit_issues` (`app/auth/permissions.py:189-190`), so delete carries no authority beyond edit, and the registered `issues.delete` (`dangerous=True`) code is never consulted.

4. **`POST /reports/<report_id>/delete`** (`app/reports/routes.py:151`) — irreversible hard delete of a report, all sections, all attachments and all S3 objects, gated by a single per-project flag (`can_archive_reports`) with no RBAC layer and, unlike `detail`/`edit`, without `_require_can_read`'s `Project.deleted_at` check.

5. **All 7 `daily_report_create_v2` routes** — no module gate at all (see D-0 below). The per-project `can_create_report` inside `_project()` (`app/reports/create_v2.py:33`) is present on all 7, so no route is *currently* unguarded, but there is no module-level backstop: a future route added to this blueprint that forgets `_project()` would be reachable by any authenticated user.

*(Every other write route in scope has a proven per-project capability check cited in the table. No route in scope has a proven RBAC check on a write path — RBAC appears only on three read routes: `reports.today`, `reports.configuration_hub`, `projects.dashboard`.)*

## C. Routes taking an ID with no owns-resource check

1. **`POST /reports/projects/<project_id>/reports/create`** (`app/projects/routes.py:130-133`) — takes `project_id`, resolves it, performs no ownership/capability check.

## D. Routes whose checks differ from an immediate sibling

### D-0 — v1 vs v2: the module gate (the one structural divergence)

Reading `register_blueprints` (`app/__init__.py:122, 127-130`) and the hook's prefix tuple (`:179`): `projects.`, `reports.`, `issues.`, `attachments.` are all in the tuple; `daily_report_create_v2.` is not, and `app/reports/create_v2.py` (135 lines, read in full) contains no `@bp.before_request` and never imports `can_access_reports_module`. **PRE-011 confirmed, not fixed.** The mechanism is the endpoint-name keying: the blueprint lives in `app/reports/` but is named `daily_report_create_v2`, so `"reports."` does not match it.

Practical exploitability today is narrow and I state it explicitly rather than inflating it: `can_access_reports_module` (`app/auth/permissions.py:51-56`) passes on `has_any_project_capability(user, ("can_view_reports","can_create_reports"))`, so any user who satisfies `can_create_report(user, project_id)` (`:150-151` → `user_has_project_capability`, `project_memberships.py:78-89`) necessarily also satisfies the module gate. The gate therefore adds no denial for these 7 routes as currently written. The gap is the *absence of a backstop*: this is the only blueprint in its family with no module-level check, so the entire authorization of a report-creating, presigned-URL-issuing JSON API rests on one helper (`_project()`) being called by hand in all 7 handlers.

## Performance / correctness observations (evidence-backed, not authorization)

- **Unbounded result sets, no pagination:** `reports.index:51`, `projects.reports:98`, `issues.index:42-44`, `projects.issues:200`, `reports.today:80-85`, `projects.index:48` all end in `.all()` with no `limit`/`offset`.

## Needs verification

1. **Is a `CUSTOM` `ProjectUser` row with `can_view_project=True, can_view_issues=False` actually creatable through the admin UI?** The D-2 `issues.index` leak depends on it. `PROJECT_ROLE_PRESETS` (`app/project_memberships.py:36-43`) never produces that combination — all 6 presets that include `can_view_project` also include `can_view_issues`. *Proof needed:* read `admin.projects_memberships` (`app/admin/routes.py:257+`, outside this unit's scope) and confirm whether individual `CAPABILITY_FIELDS` checkboxes are persisted independently of a preset. If they are not, the finding drops to Info (unreachable state).
2. **Whether any deployed operator process runs `flask cleanup-expired-report-upload-sessions` on a schedule.** Determines whether v2's missing cancel-time cleanup (D-1) leaks storage indefinitely or is swept within a day. FOUNDATION-B §6 established no in-app scheduler exists; a cron/systemd timer outside the repo would change the impact. *Proof needed:* deployment manifests / crontab, not in this repo tree.
3. **Exploitability of the `attachments.delete` open redirect (`app/attachments/routes.py:91`).** It is POST-only behind global CSRF, so a plain cross-site link cannot reach it. *Proof needed:* whether any template renders a `next` hidden field from a URL query parameter, which would let an attacker seed the value via a link to `reports.edit`. I grepped `app/templates/reports/form.html` for the upload/limits attributes but did not audit every template in the repo for a `next` field — treat as unconfirmed.

This is documented admin-bypass behavior, so I have not flagged it — but a hard, unrecoverable delete is the one place where bypass-vs-confirm deserves a product decision. *Proof needed:* `AGENTS.md` product spec on report deletion authority (not read in this pass).
5. **PostgreSQL behaviour of the `FOR UPDATE` lock ordering in `finalize_daily_report_create_v2`** (`app/reports/services.py:182-185`: session locked, then items locked) versus `parse_report_attachment_manifest` (`app/reports/direct_uploads.py:227-233, 260-262`: same order). Both take the same order so a deadlock between the v1 and v2 finalize paths looks unlikely, but the tests run on SQLite where `with_for_update()` is a no-op (`tests/conftest.py`, per CLAUDE.md). *Proof needed:* a concurrency test against real PostgreSQL.

## Explicitly checked and found clean

- **Authentication coverage:** all 36 routes require a session; the 4-entry public allowlist (`app/__init__.py:153`) contains none of them.
- **CSRF:** global `CSRFProtect`; grep for `csrf` across all of `app/` found no `exempt` call. The v2 JSON API is *not* exempt, and `daily-report-create-v2.js:77` sends `X-CSRFToken` — so the JSON flow genuinely relies on CSRF, not on an exemption.
- **Session/item ID binding in both upload flows:** fully re-validated in every route (see C, trap (b)) — `_session` `direct_uploads.py:43`, item `:173`, finalize `services.py:182-190`, manifest `direct_uploads.py:227-235, 265-275`. This is the strongest part of the module.
- **Mass assignment:** `_assign_issue_fields` (`app/issues/services.py:99-122`) and `_assign_report_fields` (`app/reports/services.py:601-610`) both enumerate fields explicitly; neither reads `project_id` from the form. `create_issue` forces `project_id=project.id` `issues/services.py:41`; `finalize_daily_report_create_v2` forces `project_id=project.id` `services.py:191`. No route in scope can move a record between projects.
- **Cross-project child references:** `report_category_id`s are re-verified against `project.id` in `validate_daily_report_create_v2_payload` `services.py:111-113`, `validate_categories` `services.py:574-584`, and `validate_report_form` `services.py:833-847`. `owner_user_id` is re-verified as an active member of the target project `issues/services.py:144-165`.
- **SQL injection:** every query in all 5 route files and both service files is SQLAlchemy expression-language; no `text()`, no f-string/`%`-formatted SQL, no `.filter(...)` built from a raw request string. Date filters go through `parse_iso_date`/`parse_report_date`; `PersistentIssue.opened_date >= date_from` (`issues/routes.py:206`, `projects/routes.py:312`) passes an unparsed string to a `Date` comparison — a bind parameter, so not injectable (it can raise a DB cast error on Postgres; noted as robustness, not injection).
- **XSS:** grepped `app/templates/reports/` and `app/templates/issues/` for `|safe` and `autoescape` — **zero** matches. Jinja autoescaping is on for `.html`; the `|tojson` uses in `reports/form.html:12,19,62,78,79` are Flask's HTML-safe `tojson` inside single-quoted attributes.

- **Sensitive-data logging:** the only logging call in scope is `current_app.logger.exception("daily_report.media_dispatch_failed job_id=%s", job_id)` (`app/reports/services.py:728`) — a job ID, no presigned URL, no filename, no PII. Presigned URLs are returned in responses but never logged.
