# ENDPOINTS.md — Combined per-route authorization matrix

Read-only. Merges `.audit/ENDPOINTS-g1.md` (auth, admin, admin_storage, users,
account, modules, media_display_preview), `.audit/ENDPOINTS-g2.md` (reports,
projects, daily_report_create_v2, issues, attachments), `.audit/ENDPOINTS-g3.md`
(project_documents, company_media, dashboard, dashboard_api), and
`.audit/ENDPOINTS-g4.md` (customers, project_operations, partners,
partner_companies, partner_fields, partner_field_collections,
partner_relations) into one artifact, per your instruction that this is now
the audit's central document: `FOUNDATION-A2.md` §3 (no data-layer project
scoping), `FOUNDATION-B.md` §1 (no project separation in object keys), and
PRE-002 (every route hand-rolls its own check) together mean the per-route
check documented here is the *only* defense for the overwhelming majority of
this codebase.

Every row from all four source files is reproduced below, unmodified,
grouped by the same four subagent scopes. Nothing has been dropped or
condensed. The four raw per-group files remain on disk with their full
narrative detail (caveats, "explicitly checked and found clean" sections,
performance notes); this file's table is the complete row set, and the
lists that follow re-sort every A/B/C/D item from all four groups by blast
radius rather than by group.

**Total routes covered: 232** (Group 1: 53, Group 2: 36, Group 3: 55 [24
project_documents + 24 company_media + 7 dashboard/dashboard_api, with
some GET/POST pairs sharing one URL rule], Group 4: 88 [68 URL rules, GET
and POST split into separate rows]). Counts are each subagent's own,
cross-checked against `flask --app run.py routes` by that subagent, not
re-derived here.

## Unit 6b required deliverable — cycle/depth handling in `partner_relations.tree` (`app/partner_relations/routes.py:145`)

Reproduced from Group 4 in full, since this is a specifically-mandated deliverable:

**No recursive CTE, no depth limit, no visited set exists at read time.** `_build_department_tree`'s `build_department()` (`routes.py:341-350`) recurses over `parent_department_id` chains with none of the three; `_visible_department_ids` (`:372-377`) walks ancestors in a `while` loop with **no visited set** (a two-node cycle hangs a worker indefinitely); `_department_subtree_ids` (`:381-392`) has the same defect. The database provides no backstop (`CompanyDepartment.parent_department_id` is a bare self-referential FK, `ondelete=SET NULL`, no check constraint — confirmed in `FOUNDATION-A2.md` §1/§2).

**Cycle prevention exists only at write time, in a different blueprint**: `app/partner_companies/routes.py:341` (`_save_department`) is the *only* HTTP-reachable writer of that column, and it correctly rejects self-parenting and descendant-parenting via a visited-set BFS (`_department_descendant_ids`, `partner_companies/routes.py:352-370`), also constraining moves to stay within one company.

**Net assessment**: the tree view terminates today only because the department writer happens to be correct elsewhere in the codebase — this is a defence-in-depth gap, not a live DoS, since no currently-reachable route can create the cycle the reader doesn't guard against. `PartnerRelationship.parent_relationship_id`'s equivalent missing constraint is **not reachable at all** — grep confirms zero routes/services read or write that column; it is dead. The partner-level `parent_partner_id` graph *does* have an application-level cycle check (`_creates_cycle`, `partner_relations/routes.py:490-507`) but it is defeatable because no uniqueness constraint on `(company_id, partner_id)` lets a partner hold two relationship rows with different parents, letting a 3-node cycle evade the single-parent-edge assumption the checker makes — bounded in impact because nothing renders `parent_partner_id` recursively (only `parent_department_id` does).

Full reasoning and worked exploit trace: `.audit/ENDPOINTS-g4.md`, "Unit 6b required deliverable" section.

## Combined findings, re-sorted by blast radius across all four groups

### CRITICAL — real privilege escalation or auth bypass, reachable today

1. **[G1]** `POST /admin/users/<user_id>/edit` — an `ADMIN` can grant themselves the `SUPER_ADMIN` role: `role_id` is accepted from the form with no server-side allow-list, and `ensure_not_last_active_super_admin` only blocks *removing* the last active super admin, never *granting* the role. Full account-type takeover.
2. **[G1]** `POST /admin/users/<user_id>/reset-password` — an `ADMIN` can reset a `SUPER_ADMIN`'s password and read the plaintext temporary password from the flash message, with no target-role restriction of any kind. Direct account takeover.
3. **[G1]** `POST /admin/roles/<role_id>/permissions` — any holder of `roles.manage` can rewrite the `ADMIN`/`VIEWER_ADMIN` system roles' grants (only `SUPER_ADMIN`'s own role is excluded), including their own role, enabling self-grant of any permission code in the registry.
4. **[G1]** `POST /admin/projects/<project_id>/memberships` — any holder of `project_assignments.manage` can insert themselves into *any* project with the full 17-flag capability set (`PROJECT_OWNER`-equivalent), with no check they hold the capabilities being granted, and the route is not even covered by the reports module gate (the gate's own allow-list names a non-existent endpoint, `"admin.projects_memberships"`).
5. **[G3]** `POST /company-media/albums/<album_id>/permissions` — a user whose *only* authority is an ACL `can_share` row on one album can grant themselves (or an entire role) `can_edit`/`can_delete`/`can_upload`/`can_download` on that album, because `company_media`'s `_can()` treats a bare ACL match as sufficient with no RBAC/module backstop — unlike the parallel `project_documents` mechanism, which the paired comparison in Group 3 shows *does* have that backstop.

### HIGH — real IDOR, irreversible action, or authorization gap with meaningful reach

6. **[G4]** `POST /projects/<project_id>/contractors/<role_path>` — binds any active `ProjectContractor` by client-supplied ID to a project the caller can merely *read*, with no `can_access_contractor` check; the resulting assignment then makes that contractor's PII (name/phone/email/address) visible, and potentially editable, to the attacker via the now-satisfied `accessible_contractors_query` visibility rule.
7. **[G2]** `POST /reports/<report_id>/delete` — an irreversible **hard delete** (no soft-delete column exists on `DailyReport` at all, by a deliberate earlier migration) of a report, all its sections, all its attachments, and their S3 objects, gated by a single per-project flag (`can_archive_reports`) with zero RBAC layer, and — unlike its `detail`/`edit` siblings — without even the `Project.deleted_at` re-check those routes perform.
8. **[G2]** The entire `daily_report_create_v2` blueprint (7 routes: create_session, preflight, session_state, presign, complete, cancel, finalize) has **no module-level gate** — neither the global hook nor its own `before_request` (PRE-011, confirmed not fixed). Every route is currently backstopped by an identical per-project `can_create_report` check, so practical exploitability is narrow today, but there is no defense-in-depth layer behind that single helper, unlike every sibling reports-module blueprint.
9. **[G2]** `POST /attachments/<attachment_id>/delete` — permanently deletes an attachment and its S3 bytes with only `can_edit_report`; the `report_attachments.delete` RBAC code the UI itself gates the delete button on is never checked server-side.
10. **[G3]** `POST /project-documents/folders/<id>/files/bulk-archive` and `/bulk-restore`, and the identical `company_media` pair — the *route*-level gate is view-only (`can_view_project_document_folder`/`p.view_album`); delete/restore authority is proven only per file, inside the service layer. Currently safe because the per-file check is real and always runs, but the route-level permission name (view) doesn't match the action performed (delete), which is exactly the shape that breaks silently if a future refactor moves the per-file check.
11. **[G4]** `POST /customers/<cid>/projects/<pid>/move` — re-parents a project between customers while checking only `can_access_customer` (a read-shaped check) on the *source* customer; the *target* customer correctly requires `can_manage_customer`. A `PROJECT_VIEWER` holding the global `customers.edit` RBAC code can move a project out of a customer they have no management authority over.
12. **[G2]** `POST /reports/issues/<issue_id>/delete` — `can_delete_persistent_issue` resolves to the exact same capability as `can_edit_persistent_issue` (`can_edit_issues`); the dedicated, `dangerous=True` `issues.delete` RBAC code that exists in the registry specifically for this action is never consulted by any route.
13. **[G2]** `POST /reports/projects/<project_id>/reports/upload-sessions/<session_id>/cancel` — triggers `cleanup_expired_sessions(dry_run=False)` with **no user or project filter at all**: one authorized POST for project A causes synchronous S3 deletes and DB cleanup across every user's and every project's expired/cancelled Daily Report upload sessions.
14. **[G1]** `GET /admin/projects/<project_id>/reporters` / `/memberships` — loads and renders the full project-membership roster plus a directory of every active user's full name, username, **email**, and role, gated only by the global `projects.view` permission with zero verification the caller has any relationship to the specific project in the URL.

### MEDIUM — weaker-than-sibling check, missing audit trail, information disclosure, or exploitable-but-low-impact inconsistency

15. **[G2]** `GET /reports/issues` and `GET /reports/today` — both scope their *visible row set* by a different capability than the one their entry gate checks (`can_view_project` vs. `can_view_issues`/`can_view_reports` respectively), so a CUSTOM `ProjectUser` row combining the two unevenly can see issue/report existence across a project it shouldn't.
16. **[G3]** `GET /reports/dashboard/contractors/<contractor_id>` — issue visibility is gated by the *global* `has_any_project_capability(can_view_issues)` rather than the correct per-project check its sibling `project_dashboard_context` uses; a member with `can_view_issues` on project A and only `can_view_project` on project B sees B's issue titles rendered in the contractor dashboard template.
17. **[G3]** `POST /company-media/files/<file_id>/signed-preview` — omits the `is_active`/`file.deleted_at` check every sibling company_media file-permission function performs, and its `variant="preview"` branch hands out the **original** video object on a view-only permission, bypassing the dedicated `.download` RBAC code and ACL flag.
18. **[G1]** `POST /admin/users/new` — `role_id` accepted with no allow-list (same underlying gap as finding #1, but on creation rather than edit — an `ADMIN` can directly create a new `SUPER_ADMIN` account).
19. **[G3]** Paired `set_folder_permission` (project_documents) vs `set_permission` (company_media) comparison: company_media writes **no audit row** on either grant or revoke, has a `can_download` flag with no project_documents equivalent, and (per finding #5) has no RBAC/module backstop on the ACL evaluation path — three concrete, itemized divergences between two functions doing the same job.
20. **[G4]** `POST /partner-companies/<company_id>/edit` — the only mutating route in its file with no active-company guard; combined with the checkbox-default bug (below), this can silently re-activate an archived company (`is_active=True`) while `deleted_at` remains set, creating exactly the two-flag disagreement `FOUNDATION-A2.md` §2 warned about.
