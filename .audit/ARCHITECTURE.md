## 1. Stack, package managers, build, run

- **Language/runtime**: Python 3.12, Flask 3.0 full-stack (Jinja2 server-rendered
  HTML, no SPA/API-first split). `requirements.txt` pins all Python deps
  (`Flask==3.0.3`, `Flask-SQLAlchemy==3.1.1`, `Flask-Migrate==4.0.7`,
  `Flask-Login==0.6.3`, `Flask-WTF==1.2.1` (CSRF), `Flask-Limiter==3.8.0`,
  `psycopg[binary]==3.2.1`, `Pillow==10.4.0`, `pillow-heif==0.18.0`,
  `celery==5.4.0`, `redis==5.0.8`, `boto3==1.35.8`, `gunicorn==22.0.0`,
  `pytest==8.3.2`). No `pyproject.toml`/Poetry — plain `pip install -r
  requirements.txt` into a venv (`README.md`).
- **Frontend**: Bootstrap 5 + Chart.js via CDN links in `app/templates/base.html`;
  first-party interactivity is plain ES modules under `app/static/js/*.js`,
  loaded directly by templates, **no bundler, no framework, no npm build step
  for the app itself**. `package.json` only carries: `esbuild`/`jsdom` as dev
  tooling, `heic-to` as a runtime dependency vendored into
  `app/static/vendor/heic-to/heic-preview.min.js` via `npm run
  build:heic-preview` (`scripts/build-heic-preview.mjs`), and `node --test
  tests_js/**/*.test.js` as the JS test runner.
- **Database**: PostgreSQL via SQLAlchemy ORM (`Flask-SQLAlchemy`), schema
  evolution via Flask-Migrate/Alembic (`migrations/versions/`, 29 revision
  files, `migrations/env.py`). Tests run against **in-memory SQLite**
  (`tests/conftest.py`), not Postgres — see §5 below, this is a trust-boundary
  gap for anything Postgres-specific.
- **Object storage**: S3-compatible (real deploys: MinIO/S3 via `boto3`),
  abstracted behind `app/storage/providers.py::StorageProvider`
  (`FakeStorageProvider` in-memory for tests/dev, `S3StorageProvider` for
  real use, `DisabledStorageProvider` as a hard-fail fallback). Selected by
  `STORAGE_PROVIDER` env var (`fake` | `s3` | `disabled`).
- **Async/background work**: Celery 5 (`app/celery_app.py`, broker/result
  backend = Redis). Queues: `media_image`, `media_video`, `storage_cleanup`,
  `bulk_download` (`scripts/start-media-worker.sh`).
- **Rate limiting**: Flask-Limiter, storage backend configurable
  (`memory://` default for local/dev, Redis recommended for multi-worker
  production — `RATELIMIT_STORAGE_URI`).
- **How it's meant to run**:
  - Local dev: `flask run` (README.md, `run.py`).
  - Production: Gunicorn (`gunicorn.conf.py`, `wsgi.py`) behind Docker Compose
    (`docker-compose.yml`: `web` + `cloudflared` services, Cloudflare Tunnel
    for ingress — **no directly exposed port**, no nginx in this compose file)
    or bare-metal Ubuntu (`DEPLOY_UBUNTU.md`). A separate `scripts/start-media-worker.sh`
    process runs the Celery worker; nothing in `docker-compose.yml` currently
    starts it automatically (worth confirming against Phase 11 scope — the
    compose file only defines `web` and `cloudflared`).
  - `docker-entrypoint.sh` runs `flask db upgrade` and admin seeding on
    container start.

## 2. Entry points

### 2.1 HTTP routes

417 raw `@bp.<verb>(...)`-style matches / **199 distinct route registrations**
across 20 blueprints (some view functions are reachable under two paths via
stacked decorators, e.g. `admin.projects_reporters`, `app/admin/routes.py:257-258`).
Blueprint registration is manual, not auto-discovered —
`app/__init__.py::register_blueprints()` (`app/__init__.py:97-131`) is the
single place a new blueprint becomes live; a module's routes are dead code
until added there.

Two routes are registered directly on `app` rather than a blueprint:
`app/__init__.py:141` (`GET /health`), `app/__init__.py:145` (`GET /healthz`),
`app/__init__.py:149` (`GET /`, redirects by auth state), and
`app/__init__.py:94-95` (`POST /media-display-preview`, bound to
`app.account.routes.media_display_preview` outside the `account` blueprint's

## 3. Auth layer

Authentication: session-based via Flask-Login (`app/extensions.py:10`),
password hashes via Werkzeug (`scrypt:`/`pbkdf2:`, enforced by
`security-audit`'s `password-hashes` check, `app/cli.py:470`). Login route
`app/auth/routes.py:18`; `load_user` callback `app/__init__.py:70-72`.

Authorization is **three layers**, and each layer's enforcement point is a
different piece of code — read all three before concluding a route is safe:

1. **Login gate** — `before_request` hook `require_login`
   (`app/__init__.py:154-163`). Public endpoints: `auth.login`, `health`,
   `healthz`, `static` (`app/__init__.py:155`). Notably `request.endpoint is
   None` also bypasses (intentional — lets Flask 404 unknown routes instead of
   redirecting to login, per the comment at `app/__init__.py:157-158`).

2. **Module gate** — second `before_request` hook `require_reports_module_access`
   (`app/__init__.py:166-179`). Maps endpoint-name **prefixes** to a module
   check: `"dashboard.", "dashboard_api.", "projects.", "reports.", "issues.",
   "attachments.", "customers.", "project_operations."` (`app/__init__.py:174`)
   plus an explicit allow-list of `admin.*` project/category-admin endpoints
   (`app/__init__.py:175-180`) — all funnel through
   `can_access_reports_module()` (`app/auth/permissions.py:53-57`). Equivalent
   gates exist per-module as plain functions (`can_access_partners_module`,
   `can_access_project_documents_module`, `can_access_company_media_module`,
   `app/auth/permissions.py:65-77`) but those are **not** wired into a global
   `before_request` — they're called at the top of each blueprint's own
   routes (verify this holds for every route in `partners`, `project_documents`,
   `company_media`, not just the index view — a route added later without
   copying the check at the top would be reachable).

3. **Global roles + DB-backed RBAC** — `UserRole` enum (`SUPER_ADMIN`, `ADMIN`,
   `VIEWER_ADMIN`; `PROJECT_MANAGER`/`REPORTER` legacy-only,
   `app/models/enums.py:4-9`). `User.role_id` is a single FK to `Role`
   (`app/models/user.py:21`, `app/models/rbac.py:7-17`) — one global role per
   user, `legacy_role` column is a compatibility mirror only, never read for
   authorization (`app/models/user.py:10-11, 20`). Permission catalogue is
   code (`app/permissions/registry.py`), synced into `permissions`/`role_permissions`
   tables only by explicit `flask sync-permissions` — **never automatically at
   startup** (`app/__init__.py` has no such call). Check primitive:
   `User.can(code)` → `user_has_permission()` (`app/permissions/services.py:14-28`),
   which **short-circuits true for `SUPER_ADMIN`** (`app/permissions/services.py:16-17`,
   confirm this is intended for every single dangerous permission, including
   ones added later) and caches the permission-code set on Flask's `g` per
   request. `permission_required(code)` decorator (`app/permissions/services.py:31-38`)
   is used by `admin`, `admin_storage`, `users`, and all `partner_*` blueprints.
   `role_required`/`viewer_or_admin_required`/`super_admin_required`
   (`app/auth/permissions.py:15-35`) are role-code decorators, defined but not
   obviously used by any route in the current inventory above — confirm they
   are genuinely dead or find their call sites with a repo-wide grep before
   the deep pass.

4. **Per-project capability flags** — `app/project_memberships.py`. Global
   admins/viewer-admins bypass this (`has_global_project_scope`,
   `app/project_memberships.py:44`+); everyone else's access to a *specific*
   project comes from a `ProjectUser` row's boolean flags
   (`CAPABILITY_FIELDS`, `app/project_memberships.py:8-14`), assignable via
   named presets (`PROJECT_ROLE_PRESETS`, `app/project_memberships.py:34-41`)
   or `CUSTOM`. Core check: `user_has_project_capability()`; wrapped by
   `app/auth/permissions.py` into per-action helpers (`can_read_project`,
   `can_edit_report`, `can_create_persistent_issue`, `can_view_issue`, ...)
   which routes in `reports`, `issues`, `projects`, `attachments` call inline
   (no decorator). `project_read_required`/`project_write_required`/
   `project_manage_required` (`app/auth/permissions.py:225-249`) exist as
   decorator wrappers around this layer but, per the route inventory in §2.1,
   are not visibly applied to any current route — same caveat as above, grep
   for call sites before assuming dead code.

5. **Trusted-host guard** — only active if `TRUSTED_HOSTS` is set
   (`app/__init__.py:182-195`); always augmented with loopback hosts for
   Docker healthchecks. If unset (default), this guard is a no-op — confirm
   production `.env`/secrets set it.

6. **CSRF** — Flask-WTF `CSRFProtect` global (`app/extensions.py:11`,
   `csrf.init_app(app)` at `app/__init__.py:68`). Every state-changing
   template form includes a hidden `csrf_token()` field (spot-checked across
   `company_media`, `project_documents`, `admin/projects/reporters.html`
   templates). JSON-only endpoints (direct-upload presign/complete flows)
   rely on Flask-WTF's exemption/handling for non-form content — verify this
   explicitly for `app/reports/create_v2.py` and `app/reports/direct_uploads.py`
   during the deep pass, since JSON POST + CSRF is a common AI-agent mistake
   (either forgetting the header contract client-side, or silently exempting
   the view).

7. **Security headers** — CSP/`X-Frame-Options`/`X-Content-Type-Options`/
   `Referrer-Policy` set in `after_request` (`app/__init__.py:198-224`). CSP
   `script-src`/`style-src`/`font-src` allow `cdn.jsdelivr.net` +
   `fonts.googleapis.com`/`fonts.gstatic.com` (Bootstrap/Chart.js/fonts by
   CDN — a supply-chain trust boundary, see §5). `connect-src`/`img-src`/
   `media-src`/`frame-src` are widened at runtime only to the configured S3
   endpoint origin (`storage_connect_source`, `app/security.py:10-17`), which
   validates the endpoint has no embedded credentials before trusting it.

8. **`flask security-audit`** (`app/cli.py:390-483`) is itself a
   self-check of most of the above (secret key strength, cookie flags, CSRF
   init, security headers, rate-limit backend, storage provider not `fake` in
   prod, Celery eager mode, RBAC schema presence, password hash algorithm,
   presence of an active `SUPER_ADMIN`, absence of demo data) — read its
   output for the target environment before trusting any of layers 1-7 there.

## 4. Data layer

- **ORM/query style**: SQLAlchemy declarative models under `app/models/*.py`,
  re-exported through `app/models/__init__.py` (import from `app.models`, not
  submodules). Mixins: `TimestampMixin` (created/updated), `CreatedAtMixin`,
  `SoftDeleteMixin` (`deleted_at`) — `app/models/mixins.py`. Most write paths
  go through a `services.py` per module rather than raw queries in routes
  (`app/reports/services.py`, `app/partners/services.py`,
  `app/project_documents/services.py`, etc.) — the largest, `app/reports/services.py`
  (894 lines) and `app/cli.py` (1228 lines) are worth prioritizing for
  transaction/consistency review.
- **Migrations**: Flask-Migrate/Alembic, 29 revision files under
  `migrations/versions/`, oldest `20260708_0001_initial_schema.py`, newest by
  filename `20260725_0026_...` plus three hash-named revisions for later
  features (customers/grouping, contractors, project-update timeline) —
  **confirm actual head and linear history with `flask db history` /
  `alembic heads`, do not assume filename date order is the real DAG order.**
- **Multi-tenancy**: none in the SaaS sense — this is a single-organization
  internal tool. The nearest thing to tenancy is **project membership**
  (`ProjectUser`) scoping report/issue/document visibility, and `Customer` /
  `Company` as CRM groupings, not isolation boundaries. There is no
  `tenant_id`/`org_id` column anywhere in `app/models/`.
- **Tests use SQLite in-memory** (`tests/conftest.py:14`), production is
  Postgres. Anything relying on Postgres-only behavior (JSON/JSONB operators,
  case-sensitive collation, `ON CONFLICT`, sequence behavior after
  `reset-database` — see `sync_postgres_sequence`, `app/cli.py:487`, needed
  precisely because SQLite/Postgres autoincrement diverge) is **not**
  exercised by the test suite and needs separate verification against real
  Postgres.
- **File storage**: exclusively S3-compatible object storage behind
  `app/storage/`. Object keys are deliberately opaque —
  `app/storage/keys.py::build_original_key` etc. never place raw user
  filenames into the key path, only into DB metadata
  (`app/storage/keys.py:53-64`, comment at line 54-56 states this is
  intentional to prevent path-traversal-via-filename from ever reaching S3
  keys). `app/storage/validation.py::validate_file_metadata` whitelists
  extension→MIME pairs (`ALLOWED_FILES`, `app/storage/validation.py:11-19`)
  and enforces per-category size caps from config. **Client-declared
  MIME/size/checksum is still client-declared** — confirm server-side
  re-verification exists at the "complete upload" step (not just at
  "presign"), since presigned-PUT flows let the browser upload directly to
  storage before the app ever sees the bytes.
- **Audit trail**: `app/audit.py::log_audit` writes `AuditLog` rows
  (actor, action, entity, before/after JSON, IP, user-agent). **IP address is
  read from `request.headers.get("X-Forwarded-For", request.remote_actor)`
  directly** (`app/audit.py:33`), bypassing `ProxyFix`'s trusted-hop handling
  that's set up in `app/__init__.py:73-75` for `TRUST_PROXY_HOPS`. If
  `TRUST_PROXY_HOPS` is 0 (the default) or the header isn't stripped by an
  edge proxy, a client can put an arbitrary value in `AuditLog.ip_address` —
  flag for the deep pass, this affects forensic trust in the audit log
  itself, one of the "crown jewels" in §6.

## 5. Trust boundaries and untrusted input

- **Every HTTP request body/query/form/JSON** from an authenticated-but-untrusted
  browser session — the overwhelming majority of input. Includes IDs in URL
  paths (`<int:project_id>` etc. — Flask's converter guarantees int type but
  **not** that the caller is allowed to see that ID; every such route is an
  IDOR candidate and must be checked against the three-layer model in §3).
- **File uploads** — three parallel upload surfaces (Daily Report attachments
  via `app/reports/direct_uploads.py`/`create_v2.py`, Project Documents via
  `app/project_documents/routes.py`, Company Media via
  `app/company_media/routes.py`), all using presigned-PUT-to-S3 + a
  "complete"/"finalize" callback. The presign step trusts client-declared
  filename/MIME/size (validated against `ALLOWED_FILES` + size caps, §4); the
  actual bytes never transit the Flask app for the direct-upload path, so
  **any content-sniffing/malware-scanning must happen post-upload if it
  exists at all** — check whether one does.
- **Avatar/branding image upload** (`app/account/routes.py`,
  `app/display_images.py`) — this one *is* proxied through the app
  (`Image.open(...).verify()` at `app/account/routes.py:61`), a different,
  narrower trust boundary than the presigned-S3 paths — Pillow decompression-bomb
  and format-confusion risk lives here specifically.
- **CSV export** (`admin_storage.export_csv`, `app/admin_storage/routes.py:28`)
  — output encoding/injection (formula injection in spreadsheet consumers) is
  a relevant check.
- **Search/filter query params** (`q=` on customers/partners/documents indexes)
  — used in SQLAlchemy `filter`/`ilike` calls per `services.py` files; confirm
  parameterization (SQLAlchemy ORM generally protects this, but raw `func`/
  `text()` usage anywhere would be the exception to hunt for).
- **CLI operator input** — `flask` command `--option` values run with local
  filesystem/DB trust; still confirm `--confirm` string-matching
  (`_require_reset_confirmation`, `app/cli.py:283`) can't be bypassed by
  whitespace/case tricks.
- **Third-party script/style origins in the CSP** (`cdn.jsdelivr.net`,
  Google Fonts, §3.7) — a supply-chain trust boundary distinct from the
  app's own code; a compromised CDN asset would execute with the page's
  privileges.
- **Redis** (Celery broker/result *and* optionally rate-limit storage) and
  **Postgres** are both assumed-trusted infrastructure with no additional
  authentication shown in this repo beyond connection-string credentials —
  confirm network isolation at the Phase 11 deployment layer, it's outside
  this repo's control.
- **Cloudflare Tunnel** (`docker-compose.yml` `cloudflared` service) is the
  actual internet-facing edge — the Flask app itself binds only inside the
  Docker network (`gunicorn.conf.py`), so anything Cloudflare doesn't filter
  reaches Flask directly with no other reverse proxy/WAF visible in this repo.

## 6. Crown jewels

- **Secrets**: `SECRET_KEY` (session signing), `DATABASE_URL`,
  `STORAGE_ACCESS_KEY_ID`/`STORAGE_SECRET_ACCESS_KEY`, Cloudflare tunnel
  token (`docker-compose.yml` secrets block), all read via
  `read_secret()`/`*_FILE` Docker-secret convention (`app/config.py:12-24`) —
  good pattern, confirm no code path logs these (`flask worker-config-check`,
  `security-audit` deliberately avoid printing values, per their `check()`
  design at `app/cli.py:393`).
- **PII**: `User` (full name, email — `app/models/user.py`), `Partner`
  (name/phone/email/photo — `app/models/partner.py:53-95`), `Customer`
  (`app/models/customer.py`), employee-like `CompanyDepartment` rows seeded
  by `flask seed-partner-demo` (synthetic, but shows the data shape).
- **No payment/money flow** exists in this codebase — no billing, invoicing,
  or financial transaction model found in `app/models/`.
- **Admin-only paths**: everything under `/admin/*` and `/admin/storage/*`
  (user/role/permission management, project/category admin, branding),
  gated by `permission_required("users.manage"|"roles.manage"|...)` — see the
  full table in §2.1. `SUPER_ADMIN` bypasses the RBAC permission table
  entirely (§3.3) — a `SUPER_ADMIN` account compromise is total compromise.
- **Anything that writes to storage or deletes data**: all upload
  "complete"/"finalize" endpoints (§2.1, §5), all `*_archive`/`*_delete`/
  `*_restore` routes across `partners`, `partner_companies`, `customers`,
  `project_documents`, `company_media`, `reports`; the destructive CLI
  commands in §2.2 (`reset-database`, `reset-local-dev`,
  `dev-purge-deleted-reports`); Celery `bulk_download.build_zip` (reads
  potentially many objects and writes a temp ZIP, `BULK_DOWNLOAD_MAX_FILES`/
  `BULK_DOWNLOAD_MAX_TOTAL_BYTES` caps apply, `app/config.py`).
- **Audit log integrity** itself is a crown jewel here (it's the thing that
  would be relied on to reconstruct an incident) and has the IP-spoofing
  caveat noted in §4 — worth an explicit finding either way.
