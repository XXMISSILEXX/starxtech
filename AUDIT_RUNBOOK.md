# PHASE 10 — AUDIT RUNBOOK

Quy trình audit / code review / security check cho codebase do AI agent sinh ra,
chuẩn bị cho Phase 11 (Docker + object storage + server thật).

**Nguyên tắc xuyên suốt:**
1. Tool chạy trước, Claude đọc sau. Tool bắt pattern & CVE; Claude bắt logic nghiệp vụ.
2. Read-only tuyệt đối. Không audit và sửa trong cùng một session.
3. Không finding nào tồn tại nếu không có `file:line` + code thật.
4. Có **cổng xác nhận của con người** trước khi chạy audit song song.
5. Kết quả ghi ra file, không giữ trong context.

**3 file bạn thực sự phải đọc ở cuối:** `ENDPOINTS.md`, `VERIFIED.md`, `ROADMAP.md`.

## Sơ đồ luồng

```
Bước 0  Chuẩn bị nhánh + hàng rào an toàn        (bạn, 10 phút)

Bước 3  Foundation pass (auth / middleware / config / data layer)  — TUẦN TỰ
Bước 4  Ma trận endpoint × phân quyền
        ─────────── ⛔ CỔNG XÁC NHẬN #2: bạn đọc ENDPOINTS.md ───────────

```

## Bước 0 — Chuẩn bị nhánh và hàng rào an toàn

```bash
# 1. Mốc quay lui
git checkout main                      # hoặc nhánh chứa kết quả phase 9
git tag phase9-complete
git push origin phase9-complete        # nếu có remote

# 2. Nhánh audit
git checkout -b phase10/audit

# 3. Đảm bảo cây làm việc sạch — audit trên nền bẩn thì không phân biệt được
git status --porcelain                 # phải rỗng

# 4. Cách ly secret thật khỏi tầm đọc của agent
cp .env .env.backup 2>/dev/null
grep -q '^\.env$' .gitignore || echo '.env' >> .gitignore

# 5. Thả bộ kit vào repo
mkdir -p .audit scripts .claude/agents
# copy: scripts/audit-tools.sh, .claude/agents/*.md, .claude/settings.json, AUDIT_RUNBOOK.md

# 6. Chốt hash để verify read-only về sau
git rev-parse HEAD > .audit/BASELINE_SHA
```

> gia, chạy:

> và làm lại bước với chỉ dẫn read-only rõ hơn.

## Bước 1 — Chạy tool tự động

```bash
bash scripts/audit-tools.sh
```

Script tự phát hiện stack (Node / Python / Go / Rust / PHP), tự chọn tool, tự bỏ
qua tool chưa cài và **ghi rõ lý do bỏ qua**. Bạn không cần điền đường dẫn nào.

Nên cài trước ít nhất 3 tool xương sống:

```bash
# macOS
brew install gitleaks trivy jq && pipx install semgrep
# Ubuntu/Debian
sudo apt install -y jq && pipx install semgrep
# (gitleaks & trivy: tải binary từ GitHub releases, hoặc script sẽ tự fallback sang docker)
```

Sau khi chạy, **mở `.audit/01-tooling.md` và đọc mục "BỎ QUA"** — biết mình mù ở đâu.

Đọc ngay 2 thứ trước khi đi tiếp:
- `.audit/raw/phantom-packages.txt` — có package nào "KHÔNG TỒN TẠI" không? Đây là
  lỗi cực phổ biến của code AI sinh và là lỗ hổng supply-chain trực tiếp.
- `.audit/raw/gitleaks-history.json` — secret trong git history.

⚠️ `.audit/raw/` chứa secret thật, script đã tự tạo `.audit/.gitignore` để loại nó.

## Bước 2 — Claude vẽ bản đồ và TỰ ĐỀ XUẤT danh sách module

Mở Claude Code tại thư mục gốc repo. Chạy `/init` một lần (tạo `CLAUDE.md`), rồi
paste prompt sau:

```
READ-ONLY. Do not edit, create or delete anything outside .audit/.
Do not run any command that mutates the repo, the database, or a remote system.

This codebase was largely generated by an AI coding agent and has just finished
its final feature phase. I am auditing it before deploying to production.

TASK A — Write .audit/ARCHITECTURE.md:
1. Languages, frameworks, package managers, how it builds, how it is meant to run.
2. EVERY entry point with file:line — HTTP routes, GraphQL resolvers, websocket
   handlers, webhooks, cron jobs, queue consumers, CLI commands, server actions.
3. Auth layer: where authentication happens, where authorization happens, which
   middleware/guard applies to which route group. Read the actual middleware
   registration code — do not assume a global guard exists.
4. Data layer: ORM/query style, migrations, multi-tenancy scheme if any, where
   files are stored.
5. Trust boundaries and every source of untrusted input.
6. Crown jewels: secrets, PII, payment/money flows, admin-only paths, anything
   that writes to storage or spends money.
7. External dependencies at runtime: third-party APIs, queues, caches, storage.

TASK B — Write .audit/MODULES.md: a PROPOSED AUDIT PLAN. Split the codebase into
audit units yourself; I am not going to give you a module list. For each unit:

| # | Module | Paths | ~LOC | Files | Risk (Crit/High/Med/Low) | Why this risk | Shared code it depends on | Batch |

Rules for splitting:
- A unit must be small enough to audit deeply in one subagent context — roughly
  under 3,000 LOC. Split anything bigger.
- Group by trust boundary and feature, not by file type. Do not create a unit
  called "utils" that is just leftovers — attach shared code to the foundation pass.
- Rank by risk: anything touching auth, money, user data, uploads, admin, or
  untrusted input is High or Critical regardless of size.
- Assign each unit to a Batch of at most 4 units. Units in the same batch must be
  independent of each other. Put all Critical/High units in the earliest batches.
- Explicitly list any code that is shared across many units — that goes into the
  foundation pass (Step 3), not into a parallel batch.

TASK C — At the end of MODULES.md list:
- directories you did NOT read and why
- anything that looks unfinished at a glance: TODO, FIXME, stub, mock, hardcoded
  value, commented-out check, function returning a fake value
- your estimate of total audit effort

Then STOP. Report to me in chat: the stack, the size, the module table, and the
top 5 risk areas. Do NOT begin auditing. Wait for my approval.
```

### ⛔ CỔNG XÁC NHẬN #1 — bạn làm gì ở đây

Đọc `.audit/MODULES.md` và chỉnh:
- Module nào bị chia sai (gộp 2 domain khác nhau, hoặc cắt đôi 1 luồng nghiệp vụ)?
- Module nào Claude xếp Low nhưng bạn biết là nhạy cảm? Nâng risk lên.
- Có thư mục nào nó bỏ sót không? So với `git ls-files | cut -d/ -f1 | sort -u`.
- Có unit nào > 3000 LOC không? Bắt nó chia nhỏ tiếp.

Trả lời trong chat kiểu: *"Đồng ý, trừ 3 điểm: gộp #4 và #5; tách #7 thành 2; nâng
#11 lên High vì nó xử lý webhook thanh toán. Cập nhật MODULES.md rồi dừng lại."*

Kiểm tra: `git diff --stat -- . ':(exclude).audit'` phải rỗng.

## Bước 3 — Foundation pass (TUẦN TỰ, không song song)

**Đây là bước quan trọng nhất để tránh false positive.** Nếu chạy song song ngay
mà không có bước này, mỗi subagent sẽ tự đọc lại middleware một cách hời hợt và
báo "NONE FOUND" cho những thứ thực ra đã được bảo vệ ở tầng chung.

```
READ-ONLY. Read .audit/ARCHITECTURE.md and .audit/MODULES.md first.

Audit ONLY the shared foundation — the code every module depends on. Write
.audit/FOUNDATION.md. Do not audit feature modules yet.

Cover:
1. Middleware / guard / interceptor chain: exact registration order, what each one
   does, which route groups it actually applies to. Quote the registration code.
2. Authentication: token issuance, verification, expiry, refresh, revocation,
   logout, session storage. Algorithm and key handling for JWT if used.
3. Authorization primitives: the role/permission model, the helper functions, and
   whether each one is enforced server-side.
4. Input validation layer: is there a global validation pipe/schema, and does it
   actually run on every route?
5. Error handling: global handler, what leaks to the client, stack traces in prod.
6. Config & secrets loading: where env vars are read, are they validated at boot,
   what are the defaults when missing. THIS MATTERS FOR PHASE 11.
7. Data access layer: is it parameterised by default, transaction handling,
   connection pooling, tenant scoping.
8. Logging: what gets logged, does anything log tokens/passwords/PII.

For each item write a clear verdict line the module auditors can rely on, e.g.
"CONFIRMED: every route under /api/* passes through requireAuth (src/mw/auth.ts:14,
registered app.ts:52). Routes under /public/* do NOT."

End with "GUARANTEES" — a bullet list of what module auditors may assume is
already handled, and "NOT GUARANTEED" — what they must check per-endpoint.
```

Sau đó đọc `FOUNDATION.md`. Mục **GUARANTEES / NOT GUARANTEED** sẽ được truyền cho
mọi subagent ở Bước 5.

## Bước 4 — Ma trận endpoint × phân quyền

```
READ-ONLY. Using .audit/ARCHITECTURE.md and .audit/FOUNDATION.md, build
.audit/ENDPOINTS.md — one row per entry point, including cron jobs, queue
consumers and webhooks, not just HTTP routes.

| Method | Path | Handler (file:line) | Auth? | Authz check (file:line) | Owns-resource check? | Input validation | Rate limited? | Writes? | Notes |

Rules:
- "Auth?" must be PROVEN by pointing at the middleware or guard that covers this
  specific route. If you cannot find it, write NONE FOUND. Never assume a global
  middleware exists unless FOUNDATION.md confirms it.
- "Owns-resource check" = does the handler verify the requested object belongs to
  the caller, or does it trust an ID from the request? This is the IDOR column.
  Answer YES (file:line) / NO / N-A.
- "Writes?" = does it mutate data, spend money, send email, or touch storage?

After the table, three lists:
A. Every endpoint reachable WITHOUT authentication, sorted by blast radius.
B. Every write/delete/admin endpoint with no proven authz check.
C. Every endpoint that takes an ID from the request and has no owns-resource check.

Then STOP and show me lists A, B, C in chat.
```

### ⛔ CỔNG XÁC NHẬN #2

Đọc thủ công 3 danh sách A/B/C. Kinh nghiệm: bước này lộ ra phần lớn lỗ hổng
nghiêm trọng chỉ trong vài phút. Đánh dấu cái nào là cố ý (endpoint public thật)
để subagent không báo lại.

## Bước 5 — Audit song song theo module

### Cách chạy song song (3 lựa chọn, chọn 1)

**A. Subagent song song trong 1 session — khuyến nghị.**
Mỗi subagent có context window riêng, nên context của session chính không phình.

```
Read .audit/MODULES.md. Run BATCH 1 now.

Launch the security-auditor subagent IN PARALLEL, one per module in batch 1
(maximum 4 concurrent).

For each subagent, its prompt must contain:
- the module name and its exact paths
- the instruction to read .audit/ARCHITECTURE.md, .audit/FOUNDATION.md and
  .audit/ENDPOINTS.md first, and to treat the GUARANTEES section as already handled
- the leads file for that module — first generate it with:
  jq '[.results[] | select(.path | startswith("<module path>"))]' \
     .audit/raw/semgrep.json > .audit/leads/<module>.json
  and tell the subagent these are SUSPICIONS to verify manually, not findings
- the exact output path: .audit/findings-<module>.md  (each subagent writes to its
  OWN file — never the same file)

Do not summarise or edit their findings. When all are done, report only: module,
counts by severity, and anything a subagent said it could not read.
```

**B. Nhiều terminal cùng lúc** — song song thật sự, dễ kiểm soát nhất.
Audit là read-only nên **không cần git worktree**. Mở 3–4 tab terminal trong cùng
repo, mỗi tab một session `claude`, mỗi tab một module. Chi phí: bạn phải paste 4 prompt.

**C. Tuần tự** — nếu repo nhỏ (< 15k LOC) hoặc bạn muốn theo dõi sát. Chậm hơn
nhưng chất lượng như nhau.

### Quy tắc song song

| Quy tắc | Lý do |
|---|---|
| Tối đa 4 subagent cùng lúc | Nhiều hơn thì dễ rate limit, và bạn cũng không đọc kịp |
| Mỗi subagent ghi ra file riêng | Ghi chung file = mất dữ liệu do đè lên nhau |
| Không song song trước khi có FOUNDATION.md | Sẽ ra hàng loạt "NONE FOUND" sai |
| Các module trong cùng batch phải độc lập | Tránh 4 agent cùng phân tích lại 1 file chung |
| Batch Critical/High chạy trước | Nếu phải dừng giữa chừng, bạn vẫn có phần quan trọng |
| Sau mỗi batch: đọc lướt + `git diff --stat` | Phát hiện agent lạc hướng sớm |
| Gần đầy context thì `/clear` giữa 2 batch, không phải giữa 1 batch | Đứt giữa module = audit dở dang |

Kiểm tra tiến độ: `/context` trong Claude Code.

Sau mỗi batch, chạy lại lệnh trên với `BATCH 2`, `BATCH 3`…

## Bước 6 — Pass săn lỗi đặc trưng của code AI sinh

Scanner không bắt được nhóm này. Chạy sau khi xong toàn bộ batch.

```
READ-ONLY. This codebase was generated by an AI coding agent. Hunt specifically
for the failure modes that produces. Use .audit/raw/grep-signals.txt as leads but
verify everything in the source. For each item, cite file:line or write "none found".

1. Security theatre: a function named like a check (validateToken, isAdmin,
   checkPermission, verifyOwnership) that always returns true, returns early, or
   is never called anywhere. Grep for its callers to prove it.
2. Inconsistent auth: middleware on 9 routes in a group but missing on the 10th.
   Compare siblings within EVERY router file, one file at a time.
3. Validation declared but not enforced: a schema defined and never imported, or
   applied to some fields only.
4. Fake tests: tests that assert nothing, mock the unit under test, or cover only
   the happy path on security-critical functions. List them by file.
5. Duplicated logic that has diverged — same function copy-pasted in 3 files where
   only one got the fix. Use .audit/raw/jscpd.txt as a lead.
6. Placeholder secrets, default passwords, and `env === 'development'` branches
   that are reachable in production.
7. Error handling that swallows exceptions silently or leaks stack traces.
8. Dependencies that do not exist upstream, are freshly published, or pinned to a
   version that does not exist. Cross-check .audit/raw/phantom-packages.txt.
9. Every comment saying the code is temporary, simplified, mocked, or "for now".
10. Features that appear complete in the code structure but are not actually wired
    up — a handler defined but never registered, a service never instantiated,
    a config option read but never used.

Write .audit/ai-artifacts.md, ordered by risk. For #10 be especially thorough:
this is the difference between "phase 9 complete" and "phase 9 looks complete".
```

## Bước 7 — PoC chạy được (bộ lọc chống bịa lỗ hổng)

```
READ-ONLY on application code. You may only create files under .audit/poc/.

For the top 10 findings across .audit/findings-*.md and .audit/ai-artifacts.md,
write executable proof-of-concept tests that demonstrate the vulnerability against
a local instance, using the project's existing test framework.

Each test must FAIL today (proving the bug exists) and PASS after the fix.

Priority order:
1. IDOR — user A reads/updates/deletes user B's resource
2. Missing authz on write/delete/admin endpoints
3. Injection
4. Race conditions on any money/quota/coupon/inventory path — hit the endpoint
   concurrently and assert on the resulting DB state, not on the HTTP responses
5. Auth bypass — expired token, tampered token, missing token

Name each file after the finding ID. If a finding cannot be reproduced as a test,
do not fake it — add it to .audit/poc/UNREPRODUCIBLE.md with the reason.
```

Finding nào không viết được PoC → hạ confidence, không được coi là đã xác nhận.

## Bước 8 — Pass phản biện (bỏ bước này là hỏng cả quy trình)

Chạy trong **session mới** (`/clear` hoặc mở terminal khác) để nó không bị nhiễm
bởi hội thoại audit.

```
Use the finding-verifier subagent. It must have no memory of the audit.

Re-verify EVERY finding in .audit/findings-*.md and .audit/ai-artifacts.md against
the real source code. Output .audit/VERIFIED.md.

Be adversarial. Then write .audit/ROADMAP.md grouping only CONFIRMED findings:

## NOW — blocks Phase 11 deploy
## NEXT — fix within 2 weeks of launch
## LATER — technical debt, tracked not fixed

For each item: ID, one-line description, effort (S/M/L), and which other items it
should be fixed together with (so I can batch them into PRs).
```

Bình thường **20–40% finding sẽ rụng**. Nếu rụng < 10%, nghi ngờ pass phản biện
chạy hời hợt — chạy lại với subagent khác.

### ⛔ CỔNG XÁC NHẬN #3 — bạn triage

Với từng mục trong **NOW**:
- Bạn có tự đọc `file:line` và đồng ý không? Claude vẫn báo nhầm được.
- Cái nào chấp nhận rủi ro? Ghi lý do vào `.audit/ACCEPTED_RISKS.md` — có chữ ký,
  có ngày. Rủi ro được chấp nhận có ý thức khác hoàn toàn với rủi ro bị bỏ sót.

## Bước 9 — Sửa có kiểm soát

Trước khi sửa: **gỡ `.claude/settings.json` chế độ audit**, và commit toàn bộ
`.audit/` (trừ `raw/`) để giữ bằng chứng.

```bash
git add .audit && git commit -m "phase10: audit artifacts"
git checkout -b phase10/fix-critical
```

Không bao giờ nói "fix tất cả". Từng finding một, dùng plan mode (`Shift+Tab`):

```
Fix finding SEC-003 only. Show me the plan first and wait for my approval.

Constraints:
- minimal diff, no refactoring, no renaming, no changes outside the affected file
  unless strictly required
- do not touch any other finding
- after the fix: run .audit/poc/sec-003.test.ts (must now PASS) and the full test
  suite (must not regress). Show me both outputs.
```

Sau mỗi fix: **1 commit riêng cho 1 finding**, message ghi ID. Để còn revert được
đúng một thứ khi phát sinh vấn đề.

```bash
git commit -m "fix(SEC-003): enforce ownership check on GET /api/orders/:id"
```

Khi xong nhóm: chạy lại `bash scripts/audit-tools.sh` và **diff với kết quả cũ** —
đó là bằng chứng đã sửa, không phải lời Claude nói.

## Bước 10 — Exit criteria: khi nào Phase 10 được coi là xong

Chỉ sang Phase 11 khi tick đủ:

- [ ] Không còn finding Critical/High chưa xử lý, hoặc đã ghi trong `ACCEPTED_RISKS.md`
- [ ] 0 secret trong code **và** trong git history (gitleaks `--log-opts="--all"` sạch)
- [ ] 0 package không tồn tại upstream; 0 CVE mức High+ không có mitigation
- [ ] Mọi endpoint trong danh sách B và C của `ENDPOINTS.md` đã được xử lý hoặc
      xác nhận là cố ý
- [ ] Build xanh, test suite xanh, type check sạch
- [ ] Mọi PoC trong `.audit/poc/` đều PASS
- [ ] Coverage cho hot path (auth, phân quyền, upload, tiền, migration) ≥ mức bạn đặt
- [ ] `.env.example` đầy đủ, config được validate lúc boot, app fail-fast khi thiếu biến
- [ ] Không còn phụ thuộc local filesystem cho dữ liệu người dùng (sẽ vỡ khi container restart)
- [ ] Có kịch bản backup + đã thử restore ít nhất 1 lần
- [ ] Đã re-run toàn bộ tool và diff sạch so với baseline

Cầu nối sang Phase 11 — chạy prompt deploy-readiness (Docker, object storage,
config, migration, observability) **trước khi** viết Dockerfile, không phải trong lúc viết.
